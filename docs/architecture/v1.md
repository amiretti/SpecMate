# Arquitectura v1 — Workspace de agentes con SDD

Oct 14, 2026 · @Andy · Versión 1.0 (borrador)

## Contexto y objetivo

Construimos una app de escritorio local donde un ticket de Jira o GitHub (o una spec escrita a mano) se convierte en spec, plan y código mediante agentes en paralelo, y el developer solo aprueba, usando la suscripción de IA que el developer ya paga (Claude o ChatGPT).

No es un IDE. Es la cabina desde donde se orquesta el trabajo: specs, plan, tareas, agentes, diffs y aprobaciones. La edición fina de código sigue en el editor que el developer ya usa.

**Usuario objetivo:** developer profesional o semi-senior que ya usa Claude Code o Codex, trabaja en Windows, macOS o Linux, y quiere disciplina de specs sin atarse a la facturación de un IDE.

**Horizonte:** producto comercial. Todo el diseño asume distribución a terceros desde la v1, no herramienta interna.

## Requisitos no funcionales

La app tiene que correr bien en una PC de uso familiar: sin placa de video dedicada, sin Docker y sin instalar runtimes a mano. La inferencia ocurre en la nube del proveedor; la máquina local solo orquesta.

| Requisito | Objetivo v1 | Cómo se cumple |
| --- | --- | --- |
| Hardware mínimo | 8 GB de RAM, CPU de los últimos \~6 años, sin GPU dedicada | Sin modelos locales en v1 |
| Sistema operativo | Windows 10/11 x64 primero; macOS y Linux después | Electron multiplataforma |
| Dependencias del usuario | Solo Git | Node viene embebido; el instalador verifica Git |
| Instalación | Un instalador `.exe` / `.dmg`, sin Docker | Empaquetado con electron-builder |
| Consumo del shell en reposo | Por debajo de 300 MB de RAM | Objetivo a medir en el spike |
| Datos | Todo local: código, eventos, specs | SQLite por proyecto, sin backend propio |
| Red | Solo hacia el proveedor de IA y los MCP que el usuario configure | Sin telemetría por defecto |

Los modelos locales (Ollama y similares) quedan fuera de v1: exigen GPU o mucha RAM, y contradicen el requisito de PC estándar.

## Posicionamiento y diferencial

**La disciplina de specs de Kiro más la orquestación paralela de Conductor, con tu propia suscripción, en cualquier PC, sin ser un IDE.** Ningún producto relevado combina las cuatro cosas.

| Producto | Fuerte en | Hueco que dejamos aprovechar |
| --- | --- | --- |
| [Kiro (AWS)](https://tooldirectory.ai/tools/kiro) | SDD: requisitos, diseño y tareas en el repo antes de codear; hooks por eventos | Fork de VS Code centrado en el editor; facturación por créditos propia; no usa tu suscripción |
| [Conductor](https://www.conductor.build/workflows/run-parallel-claude-codes) | Agentes en paralelo en git worktrees aislados; usa tu login de Claude Code o Codex | Solo macOS; agentes independientes; sin SDD |
| Cursor / VS Code + extensión | Edición asistida en el editor | Sin SDD ni orquestación multi-agente |
| OpenHands | Plataforma completa con terminal, VS Code embebido y sub-agentes | Docker y \~2 GB de imágenes; no usa suscripción de Claude |
| CodeMie (EPAM) | Integraciones enterprise (Jira, Confluence, Git) | Plataforma server-side pesada; no es un workspace local |
| opcode / CloudCLI | GUIs sobre Claude Code | Wrappers sin metodología |

**Diferencial número uno:** del ticket al merge con el developer como aprobador, no como redactor. Un agente convierte el ticket de Jira o GitHub en spec, otro la parte en tareas, y cada tarea se despacha a un agente en su propio worktree. El developer aprueba spec, plan y diffs, y ve en vivo qué hace cada agente.

**Diferenciales de soporte:** suscripción propia (Claude o ChatGPT), Windows-first y liviano. El contexto total del workspace es infraestructura que habilita todo esto, no el argumento de venta.

## Alcance

La regla que gobierna el alcance: todo lo que ya hace bien un editor queda afuera.

**Objetivos de v1**

- Abrir una carpeta como workspace y acotar todo (agentes, terminal, MCP) a esa carpeta.
- Explorador de archivos con visor de solo lectura y diffs.
- Terminal integrada con varias pestañas.
- Chat con el contexto completo del workspace: archivos, terminal y actividad de agentes.
- Flujo SDD que arranca de un ticket de Jira o GitHub, o de una spec manual: un agente redacta la spec, otro arma plan y tareas, y el developer aprueba cada gate.
- Despacho de tareas a agentes en paralelo, cada uno en su worktree.
- Dos proveedores: Claude y OpenAI, con suscripción o API key.
- Conectores MCP configurables, con GitHub y Jira como primeros.

**No-objetivos de v1**

- Edición de código, LSP, autocompletado o debugging.
- Modelos locales.
- Backend propio, cuentas de usuario o sincronización en la nube.
- Colaboración en tiempo real entre varios developers.
- Integración con Dots (pasa a v2).

## Arquitectura general

Una sola app de escritorio con dos procesos: la interfaz y un proceso principal en Node que orquesta. Los agentes no corren en código nuestro sino en los runtimes oficiales de cada proveedor, detrás de un puerto común.

*[Diagrama no exportado: arquitectura de componentes · 4 capas. Reemplazado por los de la v2.]*

El orquestador SDD es la pieza propia de mayor valor; todo lo que pasa (archivos, terminal, agentes) entra al Event Bus y el MCP interno se lo devuelve al agente como contexto.

## Decisiones de arquitectura (ADRs)

Dieciocho decisiones fijan la v1. Las marcadas como "a validar" dependen del spike técnico de la semana 1.

| ADR | Decisión | Alternativa descartada | Por qué |
| --- | --- | --- | --- |
| 001 | Shell de escritorio en **Electron** con React + TypeScript | Tauri | Los SDKs de agentes y node-pty son Node: todo en un solo lenguaje y proceso. Tauri queda como optimización futura si el peso molesta |
| 002 | **Runtimes delegados** detrás de un puerto `AgentRuntime`: Claude Agent SDK y Codex app-server | Loop de agente propio | El loop, las tools, MCP y los sub-agentes ya están resueltos y mantenidos por los vendors; nosotros construimos la cabina |
| 003 | La app **nunca manipula tokens de suscripción**: el login lo hace el flujo oficial de cada vendor; las API keys van al keychain del SO | Login propio de Claude.ai o ChatGPT | Anthropic no permite que terceros ofrezcan su login; delegar es lo único defendible para un producto |
| 004 | **Workspace Event Bus** con event store en SQLite por proyecto | Estado en memoria | Todo lo que pasa queda registrado: habilita contexto total, auditoría, replay y la vista en vivo de agentes |
| 005 | **MCP interno "workspace"** que expone eventos, terminal y cambios al agente | Inyectar todo en el prompt | El agente consulta el contexto cuando lo necesita; no se quema la ventana de contexto |
| 006 | **Un git worktree por tarea** despachada | Todos los agentes sobre la misma copia | Aísla cambios en paralelo sin conflictos a mitad de tarea; es el patrón probado por Conductor |
| 007 | Artefactos SDD en **Markdown versionado en el repo**, compatibles con el layout de Spec Kit (a validar) | Formato propio en base de datos | Sin lock-in: las specs sobreviven a la app y se revisan en PR |
| 008 | **Visor de solo lectura** (Monaco read-only) más diffs | Editor completo | Recorta alcance a una fracción; la edición sigue en el editor del usuario |
| 009 | Integración con **Dots** diferida a v2, vía un servidor MCP expuesto por la app | Integración en v1 | No hay API pública de Dots verificada; exponer MCP remoto exige túnel o relay, fuera del alcance local de v1 |
| 010 | **El ticket es la entrada del flujo**: un agente redactor convierte un issue de Jira, GitHub o Azure DevOps en spec borrador, y el estado vuelve al ticket al hacer merge. La spec manual sigue disponible | Exigir siempre una spec escrita por el developer | Los equipos ya planifican en tableros; el developer pasa de redactar a aprobar. Lectura y escritura del ticket van por los MCP de Jira y GitHub ya previstos |
| 011 | **El costo es una restricción de primer nivel**: todo agente carga la skill `terse` (mandamientos de costo y escritura comprimida) y el lead aplica `model-routing` en cada spawn, con modelo explícito y reporte por spawn | Dejar el modelo y el estilo a criterio de cada agente | Sin regla, los agentes heredan el modelo más caro y reportan de más; el costo se multiplica por cada agente en paralelo |
| 012 | **Gadget de consumo** con fuentes oficiales por proveedor y degradación honesta: dato exacto, estado o estimación marcada como tal | Estimar todo localmente | Un indicador que muestra un número inventado es peor que uno que dice "no sé"; se decide qué aprobar mirando ese número |

**ADR-013 — Capa de configuración neutral al proveedor.** La fuente de verdad de instrucciones, roles, skills y conectores vive en un formato propio y neutral. Cada runtime recibe una proyección generada en su formato nativo. Ningún archivo específico de un vendor se edita a mano.

| Pieza | Fuente canónica | Estándar | Proyección a Claude | Proyección a Codex |
| --- | --- | --- | --- | --- |
| Instrucciones del proyecto y de cada módulo | `AGENTS.md` | [AGENTS.md, bajo la Agentic AI Foundation](https://codex.danielvaughan.com/2026/04/07/agents-md-open-standard-cross-tool-portability) | `CLAUDE.md` que importa `AGENTS.md` (Claude Code lo lee [solo si no hay `CLAUDE.md`](https://codex.danielvaughan.com/2026/05/27/agent-instruction-files-agents-md-claude-md-cross-tool-portability-codex-cli/)) | Nativo |
| Skills | `.agents/skills/<nombre>/SKILL.md` | [Agent Skills (SKILL.md), bajo la Agentic AI Foundation](https://codex.danielvaughan.com/2026/05/05/agent-skills-open-standard-portable-skills-codex-cli-cross-agent/) | Copia sincronizada a `.claude/skills/` | Nativo |
| Roles (agentes) | `.agents/roles/<nombre>.md`, formato propio | **No hay estándar** entre vendors | `.claude/agents/<nombre>.md` generado | Los orquesta nuestro runtime: rol → prompt + nivel + herramientas |
| Conectores MCP | `.agents/mcp.json` | MCP | `.mcp.json` generado | `config.toml` generado |
| Modelo | Nivel: rápido, estándar o máximo | — | Mapeo a modelos de Claude | Mapeo a modelos de OpenAI |
| Memoria, eventos, estimaciones | `.workspace/` | — | No se proyecta: lo consulta el MCP interno | Igual |

**Formato de un rol:** `name`, `description`, `tier` (nunca un nombre de modelo), `skills`, `capabilities` abstractas (leer, escribir, ejecutar, red, git) y `gates` que lo bloquean. El adaptador de cada runtime traduce las capabilities a sus herramientas concretas.

**Costo asumido:** los archivos proyectados son derivados, y lo derivado envejece mal. Mitigación: se regeneran al abrir el workspace y al cambiar la fuente; llevan cabecera `generado — no editar`; y si alguien edita uno a mano, la app lo detecta (hash distinto) y ofrece llevar el cambio a la fuente canónica en vez de pisarlo.

**Principio derivado (19/10): todo lo que se puede resolver una vez se resuelve al proyectar, no en cada uso.** Personalización, condicionales y composición se aplican cuando la app genera los archivos de cada runtime, no cuando el agente activa una skill. Cada paso en runtime es una vuelta más del modelo, una dependencia más en la máquina y un punto más de falla.

**ADR-014 — Niveles de autonomía configurables, con un piso que ninguno saltea.** El developer elige cuánto interviene; por defecto, **Supervisado**. Detalle en la sección *Niveles de autonomía*.

**ADR-015 — Checkpoint ante límite de consumo.** Cuando se acerca un límite, el trabajo se congela en disco de forma ordenada; al retomar se restaura y el checkpoint se borra. Detalle en *Costo y consumo*.

**ADR-016 — Spec Kit como motor de SDD, con preset propio `workspace-sdd` que compone sobre el core.** Principio: *componer, no bifurcar*. Los comandos `specify`, `plan` y `tasks` del core se envuelven con nuestras reglas; solo se reemplazan las plantillas (formato) y `implement` (modelo multi-agente). La constitución es la única fuente de principios, stack y barandas. Detalle en *Adopción de Spec Kit*.

**ADR-017 — Memoria del proyecto con Engram (Gentleman Programming), detrás del puerto `MemoryStore`.** Una base por proyecto, agentes en solo lectura y escrituras controladas al cerrar historia o sesión. Detalle en la idea 5.

**ADR-018 — Spec Kit se instala bajo demanda, sin prerequisito ni Python embebido.** Detalle en *Adopción de Spec Kit*.

## Modelo de autenticación multi-proveedor

El usuario elige proveedor y modo de pago en el setup; la app solo detecta y delega, nunca guarda ni reenvía credenciales de suscripción.

| Runtime | Modo | Estado legal | Cómo funciona |
| --- | --- | --- | --- |
| Claude (Agent SDK) | API key | Permitido | Key guardada en el keychain del SO, pasada al SDK |
| Claude (Agent SDK) | Login existente de Claude Code (Pro/Max) | **Zona gris**: [Anthropic no permite que terceros ofrezcan su login](https://thenewstack.io/anthropic-agent-sdk-confusion/), pero [Conductor usa el login existente](https://www.morphllm.com/conductor-ai-coding) | La app detecta una sesión ya iniciada por el usuario en Claude Code; muestra disclaimer; desactivable por build |
| Codex (app-server) | Sign in with ChatGPT | Permitido: [Codex soporta login con ChatGPT](https://developers.openai.com/codex/auth); lo usan [JetBrains](https://www.jetbrains.com/help/ai-assistant/activate-agents.html) y [Cloudflare OS](https://github.com/cloudflare/cloudflare-os/discussions/312) | El app-server oficial abre el flujo de OpenAI en el navegador y guarda la sesión en un home de Codex aislado |
| Codex (app-server) | API key | Permitido | Key en el keychain, pasada al app-server |

**Setup wizard**

1. Detecta qué runtimes están disponibles y si hay sesión activa.
2. Ofrece solo las combinaciones válidas de la tabla.
3. Prueba la conexión con una llamada mínima antes de terminar.

**Capability flags por runtime:** cada runtime declara qué soporta (sub-agentes nativos, hooks, skills, aprobación de tools). La UI se adapta: si un runtime no tiene sub-agentes nativos, el orquestador los emula despachando tareas a worktrees.

**Riesgo a cerrar antes del lanzamiento:** consulta legal sobre el modo "login existente de Claude". La política de Anthropic cambió varias veces en 2026; el producto tiene que poder lanzarse solo con API key para Claude si la respuesta es no.

## Modelo de eventos del workspace

Todo lo que ocurre en el workspace se registra como un evento inmutable con el mismo sobre: así la UI, el chat y los agentes leen una sola fuente de verdad.

**Sobre común:** `id`, `ts`, `workspaceId`, `source` (`fs` · `terminal` · `agent` · `sdd` · `mcp` · `user`), `type`, `correlationId` (la tarea o sesión a la que pertenece), `payload`.

| Fuente | Eventos | Productor |
| --- | --- | --- |
| `fs` | `file.created`, `file.changed`, `file.deleted` | Watcher (chokidar) sobre la carpeta y los worktrees |
| `terminal` | `terminal.command`, `terminal.output`, `terminal.exited` | node-pty, con salida agrupada por líneas y truncada |
| `agent` | `agent.started`, `agent.message`, `agent.tool_call`, `agent.tool_result`, `agent.approval_requested`, `agent.finished` | Adaptadores de cada runtime, normalizados |
| `sdd` | `ticket.imported`, `spec.drafted`, `spec.updated`, `plan.generated`, `task.created`, `task.dispatched`, `task.completed`, `gate.approved`, `gate.rejected`, `ticket.synced` | Orquestador SDD |
| `mcp` | `mcp.connected`, `mcp.error` | Gestor de conectores |
| `user` | `user.approved`, `user.rejected`, `user.message` | UI |

**Persistencia:** SQLite por proyecto en `.workspace/events.db`, ignorado por Git. Retención configurable; la salida de terminal se compacta a resúmenes después de N días.

**Consumo por el agente:** el MCP interno expone tools de lectura como `recent_changes`, `terminal_history`, `agent_activity` y `task_status`, todas filtrables por `correlationId` y rango de tiempo.

## Flujo SDD end-to-end

La entrada es un ticket de Jira o GitHub. El analista funcional lo analiza (reglas, riesgos, bloqueos, impacto) y el product-owner escribe la spec sobre ese análisis. El developer interviene para aprobar en tres puntos: la spec, el plan y cada diff (según el nivel de autonomía).

*[Diagrama no exportado: flujo SDD · 3 gates, despacho en paralelo. Reemplazado por los de la v2.]*

Si la spec se rechaza, el developer deja comentarios y el redactor la reescribe; no la edita a mano. Si no hay ticket, el developer puede escribir la spec y entra directo al primer gate.

Cada tarea puede ir a un proveedor distinto según su tipo o la suscripción disponible. Un diff rechazado vuelve con feedback al mismo agente y al mismo worktree. Al hacer merge, la spec se actualiza en el repo y el ticket recibe un comentario con el resultado y cambia de estado.

## Niveles de autonomía

El developer elige cuánto interviene, por proyecto y con posibilidad de cambiarlo por historia. **El default es Supervisado**: una aprobación después de cada acción importante.

| Nivel | Nombre | El humano aprueba | Para qué sirve |
| --- | --- | --- | --- |
| 0 | **Paso a paso** | Cada acción: cada archivo escrito y cada comando | Proyecto nuevo, código crítico, o calibrar confianza en los agentes |
| 1 | **Supervisado** (default) | Spec · plan · cada diff · PR | Trabajo normal |
| 2 | **Por hitos** | Spec · plan · PR. Los diffs pasan solos si sus gates están en verde | Historias conocidas, con buena cobertura de tests |
| 3 | **Plan y PR** | Plan · PR. La spec del redactor pasa sola | Tickets bien escritos, equipo con specs maduras |
| 4 | **Autónomo** | Solo el PR | Tareas repetitivas o de bajo riesgo |

**El piso: lo que frena en cualquier nivel, incluso Autónomo**

- **El PR** siempre lo aprueba un humano. Push y merge, también.
- **Comandos destructivos o fuera del worktree:** borrar, sobrescribir historia de git, tocar archivos fuera de la carpeta del workspace.
- **Zona crítica** (`project-guard` §5): baja automáticamente a Supervisado para esa tarea.
- **Seguridad Crítico o Alto:** frena hasta que el humano decide.
- **Contradicción con una ADR**, o una propuesta del `product-owner` ante fuentes que se contradicen.
- **Consumo:** arriba del 90% de la ventana semanal, cada spawn en nivel máximo pide aprobación (ver *Costo y consumo*).
- **Desvío de la estimación:** si una historia supera en más del doble los tokens o el tiempo estimados, frena y avisa.

**Cómo funciona sin el humano mirando:** en los niveles 2 a 4, lo que se aprueba solo queda registrado en el event store con su evidencia (gates, conteos, diff). El PR lleva un resumen de todo lo que pasó sin aprobación, para revisarlo de una vez.

**Configuración:** `.agents/autonomy.json` por proyecto, con override por historia desde la UI. El lead lo lee al arrancar cada historia y lo dice en una línea: *"nivel 2 · aprobás spec, plan y PR"*.

## Costo y consumo

El ahorro de tokens es un mandamiento del producto, no una optimización: cada agente en paralelo multiplica el costo de cualquier exceso.

**Mandamientos** (skill `terse`, la cargan todos los agentes)

1. No narrar entre herramientas.
2. No repetir: lo que está en un archivo se cita por `ruta:línea`.
3. No volcar código, diffs ni logs en reportes.
4. Leer lo justo: búsqueda antes que lectura, lectura con rango antes que archivo entero.
5. La suite completa corre una vez, con un solo dueño.
6. Modelo justo y explícito en cada spawn (`model-routing`).
7. Continuar un agente vivo antes que levantar uno nuevo.
8. Lo chico no se delega.
9. Prompts de spawn con extractos, no archivos enteros.
10. Reportes con tope: agentes ≤ 15 líneas; el lead ≤ 10 fuera de los gates.

Entre agentes se escribe en modo comprimido (fragmentos, símbolos, una línea por hecho). Lo que lee el developer en un gate se escribe claro y completo, aunque corto.

**Gadget de consumo**

Un indicador fijo en la barra de estado muestra tokens y costo estimado del día, y el uso del plan con su reinicio. Cada valor se muestra con su calidad: **exacto**, **estado** (solo semáforo y reinicio) o **estimado** (marcado con `~`).

| Proveedor y modo | Qué muestra | Fuente | Calidad |
| --- | --- | --- | --- |
| Todos | Tokens de hoy (entrada, salida, caché) y costo estimado, total y por agente | `usage` de cada respuesta, sumado en el event store | Exacto en tokens; costo estimado a precio de lista |
| Claude con suscripción (Pro/Max) | Ventana de sesión (5 h) y semanal (7 d): % usado y hora de reinicio | [Claude Code expone `rate_limits.five_hour` y `seven_day`](https://code.claude.com/docs/en/statusline) con `used_percentage` y `resets_at` | Exacto cuando hay dato de Claude Code; si no, estado |
| Claude con suscripción, solo SDK | Semáforo y reinicio de la ventana que manda; % al cruzar umbrales | El Agent SDK emite `rate_limit_event` con estado, reinicio y tipo de ventana; [el % solo llega al cruzar un umbral](https://claudeissues.com/issue/50518-claude-agent-sdk-expose-per-bucket-rate-limit-utilization-to-headless-sdk-consum) | Estado, con % ocasional |
| ChatGPT con login (Plus/Pro) | Ventana de 5 h y semanal: % usado y reinicio, más créditos disponibles | [`account/rateLimits/read` del app-server de Codex](https://github.com/openai/codex/pull/5302): ventana primaria de 5 h y secundaria semanal, con [`used_percent` y `reset_at`](https://mintlify.wiki/Soju06/codex-lb/api/codex-usage); en planes solo semanales la primaria viene vacía | Exacto |
| Claude u OpenAI con API key | Gasto estimado del día y del mes en USD, y límites de tasa | `usage` por respuesta y headers de rate limit de cada API | Estimado en USD |

**Cómo se consigue el dato exacto de Claude:** el Agent SDK no expone los porcentajes en modo headless, y el pedido para que lo haga [se cerró como no planificado](https://claudeissues.com/issue/50518-claude-agent-sdk-expose-per-bucket-rate-limit-utilization-to-headless-sdk-consum). Cuando el developer abre Claude Code en la terminal integrada, la app instala un `statusLine` propio que escribe ese JSON en `.workspace/usage.json`, y el gadget lo toma como fuente exacta. Entre lecturas, el gadget proyecta con los tokens locales y marca el valor con `~`.

**El consumo cambia el comportamiento del lead:**

| Uso de la ventana semanal | Qué hace el lead |
| --- | --- |
| Menos de 70% | Aplica `model-routing` normal |
| 70% a 90% | Avisa en el gadget; baja a `estándar` todo lo que no sea zona crítica |
| Más de 90% | Pide aprobación antes de cada spawn en `máximo` y antes de correr agentes en paralelo |

**Checkpoint ante límite (ADR-015)**

Cuando un límite se acerca, el lead congela el trabajo en disco antes de que el corte lo haga por él.

| Disparador | Umbral |
| --- | --- |
| Ventana de sesión (5 h) | ≥ 85% |
| Ventana semanal | ≥ 95% |
| Aviso del runtime (`rate_limit_event` de Claude, ventana de Codex) | Al recibirlo |
| Ventana de contexto de un agente | ≥ 80% |
| Manual | Botón "pausar y guardar" en la UI |

**Qué se guarda** en `.workspace/checkpoints/<historia>.md`, escrito en modo `terse`:

- Historia, nivel de autonomía y gate en el que está.
- Tareas terminadas, con su evidencia (comando, conteo).
- Por cada agente activo: worktree, rama, hash del último commit local, qué estaba haciendo y su siguiente paso.
- El id de sesión o thread de cada agente, si el runtime permite retomarlo.
- Decisiones tomadas en la sesión que todavía no están en ningún archivo.

El código no se copia: ya está en los worktrees. Antes de congelar, cada agente que escribe hace un commit local de trabajo en su rama (nunca push).

**Al retomar:**

1. El lead lee el checkpoint y verifica que el disco coincida: ramas y hashes iguales a los guardados. Si no coinciden, no retoma a ciegas: avisa qué cambió.
2. Retoma cada agente por su id de sesión si existe; si no, levanta uno nuevo con el checkpoint como prompt masticado.
3. **Borra el checkpoint solo cuando el primer paso retomado termina bien.** Borrarlo al leerlo pierde el avance si la reanudación falla.

**Contra la basura:** un checkpoint de más de 7 días, o de una historia ya cerrada, se lista en la UI para borrar. Nunca se borra solo.

**Si el corte llega sin aviso:** el event store conserva los hechos (archivos, comandos, tool calls), pero no la intención. Se pierde el siguiente paso de cada agente y las decisiones que no llegaron a un archivo, y el código puede quedar a mitad de tarea. El lead puede reconstruir un checkpoint aproximado leyendo los eventos, pero es caro en tokens y propenso a errores. **Por eso el checkpoint se dispara antes del límite: es lo que hace barato y confiable retomar.**

## Riesgos y mitigaciones

El riesgo más alto es legal, no técnico: el modo "suscripción de Claude" puede no ser viable para un producto.

| Riesgo | Impacto | Mitigación |
| --- | --- | --- |
| Anthropic restringe el uso de la suscripción en apps de terceros | Alto: se cae un diferencial | Consulta legal antes del lanzamiento; el producto funciona con API key de Claude o con ChatGPT |
| Los SDKs de los vendors cambian rápido y rompen los adaptadores | Medio | Puerto `AgentRuntime` aislado; versiones fijadas; tests de contrato por runtime |
| node-pty falla al compilar en Windows | Medio | Resolverlo en el spike de la semana 1, no al final |
| Varios agentes en paralelo agotan los límites de la suscripción del usuario | Medio | Límite configurable de agentes concurrentes; medidor de consumo visible |
| Scope creep hacia "IDE completo" | Alto | No-objetivos explícitos; cualquier pedido de edición se responde con "abrí en tu editor" |
| Capacidades desiguales entre Claude y Codex | Medio | Capability flags; la UI degrada en vez de fallar |
| Un agente ejecuta comandos destructivos | Alto | Aprobación obligatoria para shell y escritura fuera del worktree; todo queda auditado en el event store |

## Kit inicial de agentes y skills

El producto arranca con nueve roles y ocho skills genéricos, extraídos de un equipo de agentes en uso real y sin nada específico de ese proyecto. Lo único que se completa por proyecto es `project-guard`.

| Pieza | Tipo | Qué hace | Nivel base |
| --- | --- | --- | --- |
| `lead` | Rol | Conversa con el developer, decide qué delega, arma el equipo, asigna nivel, cierra | máximo |
| `functional-analyst` (AFU) | Rol | **Primera etapa:** reglas de negocio, flujos, casos borde, impacto en lo existente, dependencias, riesgos, bloqueos y preguntas abiertas. Entrega `docs/analysis/<historia>.md` con veredicto | estándar |
| `product-owner` | Rol | Análisis + ticket + fuentes → spec; partir historias | estándar |
| `architect` | Rol | Decisiones sin ADR, bordes entre módulos, deriva código↔ADR | estándar |
| `backend` | Rol | Implementa backend desde spec aprobada | estándar |
| `frontend` | Rol | Implementa UI con accesibilidad verificada | estándar |
| `qa` | Rol | Verifica contra AC; dueño de la corrida completa | estándar |
| `security` | Rol | Revisa y flaguea; bloquea en Crítico o Alto | estándar o máximo si es bloqueante |
| `scrum-master` | Rol | Mantiene verdadero el estado: tablero, épicas, tickets | estándar o rápido |
| `terse` | Skill | Mandamientos de costo y escritura comprimida; la cargan todos | — |
| `model-routing` | Skill | Niveles rápido, estándar y máximo, qué tarea va a cada uno y cuándo escalar | — |
| `project-guard` | Skill | Barandas, fuentes de verdad, zonas críticas, gates y bloqueos del proyecto | — |
| `spec` | Skill | Formato fijo de spec con topes por sección y template | — |
| `tasking` | Skill | Spec aprobada → tareas → equipo → gate → cierre | — |
| `adr` | Skill | ADR en formato Nygard y detección de deriva | — |
| `close-story` | Skill | Cierre de historia o fase con el estado verdadero | — |
| `checkpoint` | Skill | Congelar y retomar el trabajo ante un límite de consumo | — |

**AFU vs. PO.** El analista funcional responde *qué implica* el ticket (reglas, riesgos, bloqueos, impacto); el product-owner decide *qué se construye* y cómo se verifica (alcance, AC). Si el veredicto del análisis es `bloqueado`, no se escribe spec. En tickets chicos y sin reglas nuevas, el lead saltea el análisis para no gastar tokens.

**Formato de spec.** Ocho bloques fijos y numerados (cabecera, §1 fuentes, §2 valor, §3 diseño, §4 fuera de alcance, §5 criterios, §6 supuestos, §7 riesgos), con tope de líneas por bloque. La numeración no cambia nunca, porque el tasking, el QA y el cierre citan por número ("§5 AC-3"). Si una spec no entra en los topes, son dos historias.

**Niveles de modelo.** La política se escribe en niveles y no en nombres, porque el runtime puede ser Claude u OpenAI: rápido (`haiku`), estándar (`sonnet`, default) y máximo (`opus`). El mapeo a modelos de OpenAI se completa por instalación.

### Adopción de Spec Kit

Los artefactos de [Spec Kit](https://github.com/github/spec-kit) reemplazan a los propios; nuestras piezas pasan a ser un **preset** de Spec Kit (plantillas en español, modo `terse`, nuestro formato de AC) más lo que Spec Kit no cubre.

| Etapa | Spec Kit | Rol nuestro | Lo que agregamos |
| --- | --- | --- | --- |
| Principios del proyecto | `/speckit-constitution` → `memory/constitution.md` | `architect` | Reemplaza las barandas de `project-guard` §4; el resto de `project-guard` (gates, zonas críticas, bloqueos) sigue |
| Ticket → viabilidad | extensión `assess` (va, aclarar o descartar) | `functional-analyst` | Ingesta del ticket por MCP (GitHub, Jira, ADO) |
| Spec | `/speckit-specify` → `specs/<feature>/spec.md` | `product-owner` | Gate humano; propuestas ante fuentes contradictorias |
| Aclarar y testeabilidad | clarify + checklists | `product-owner` + `qa` en modo diseño | Test plan |
| Diseño técnico | `/speckit-plan` → `plan.md`, `research.md`, `data-model.md`, `contracts/` | `architect` | RFC por PR si cambia la arquitectura |
| Tareas | `/speckit-tasks` → `tasks.md` con `[P]` | `lead` | Nivel de modelo y estimación por tarea |
| Implementación | `/speckit-implement` (un solo agente) | `lead` + equipo | **Lo reemplazamos**: despacho en paralelo de las tareas `[P]`, una por worktree |
| Consistencia | analyze + `/speckit-converge` | `qa` | Gates, seguridad, cierre |

**Lo que Spec Kit no resuelve y sigue siendo nuestro:** la app, la orquestación multi-agente con niveles de modelo, la ingesta de tickets, los niveles de autonomía, el gadget de consumo, el checkpoint y la memoria.

**A cuidar:**

- **Dependencia del usuario.** El CLI de Spec Kit pide Python 3.11 y uv, y eso rompe "solo Git". Se embeben las plantillas en la app y el CLI se usa solo para mantenerlas.
- **Verbosidad.** Spec, plan, research, modelo de datos, contratos, quickstart y tareas son muchos tokens. El preset recorta: research y quickstart solo si hacen falta.
- **Constitución.** *(Corregido el 19/10.)* La plantilla del core no impone artículos: son marcadores con ejemplos como "library-first" o "todo expone un CLI". Se completa con nuestros principios.
- **Nombres de comandos.** Cambiaron entre versiones (`/speckit.plan` → `/speckit-plan`). Hay que fijar la versión.

**Implementado y probado (19/10, preset v0.2, Spec Kit 1.2.2).** Se reemplazó el enfoque *lean* del 18/10 por composición: el ahorro de los comandos cortos era de unos 4.600 tokens por feature, poco frente a perder las mejoras del core.

| Pieza | Estrategia | Qué agrega el preset |
| --- | --- | --- |
| Plantillas `spec`, `tasks`, `constitution` | Reemplazo | Formato propio en español, con los IDs de Spec Kit para que `analyze` y `converge` funcionen |
| `specify` | Envoltura del core | Ticket por MCP, análisis funcional, aviso de fuentes caras, topes, estimación, nunca `aprobada` |
| `plan` | Envoltura del core | Artefactos **condicionales** (research, data-model, contracts y quickstart solo si aportan), RFC/ADR si cambia la arquitectura, zonas críticas en el Constitution Check |
| `tasks` | Envoltura del core | AC que cierra, nivel de modelo y estimación por tarea; `[P]` estricto |
| `implement` | Reemplazo | Lo orquesta el lead: una tarea `[P]` por worktree |

**Constitución:** trae seis principios por defecto (simplicidad, Clean Architecture donde hay dominio, SOLID, verificable o no está hecho, seguridad en dos capas, fallar ruidosamente) y absorbe stack y barandas. `project-guard` quedó solo con lo operativo: repo, fuentes de verdad, zonas críticas, gates, bloqueos y conteos.

**Lo que mostró la prueba:**

- `specify preset resolve` confirma la composición: core + envoltura del preset en los tres comandos, y reemplazo en `implement` y las plantillas.
- Comandos compuestos: unas 2.800 palabras (`specify`), 1.400 (`plan`) y 1.900 (`tasks`), un costo por invocación, no por turno.
- `init` siembra la constitución con la plantilla del core **antes** de instalar el preset, e instalarlo después no la reescribe. Hay que correr `/speckit-constitution` después de instalar el preset; la app lo hará en ese orden.
- El core del plan sigue diciendo que `research.md` es prerrequisito de la fase 1. La regla de prioridad del preset lo resuelve en el texto; hay que vigilarlo en las primeras features.

**Instalación de Spec Kit en la PC del usuario (ADR-018, 19/10).** Python hace falta **solo para configurar** (`init`, instalar o actualizar el preset), no mientras trabajan los agentes. Los comandos corren scripts de bash o de PowerShell; en Windows se inicializa con `--script ps` y PowerShell ya viene con el sistema. Python solo aparece como tercer parser de respaldo en bash, después de `jq`, y no es obligatorio.

| Opción | Contra | Veredicto |
| --- | --- | --- |
| Prerequisito (el usuario instala Python, uv y Spec Kit) | Rompe "solo Git"; los devs de Windows y .NET muchas veces no tienen Python; cada uno con su versión | Solo como respaldo |
| Embeber Python o uv en el instalador | Suma entre 40 y 60 MB, o 63 MB en el caso de uv, a cada instalación por una herramienta de un solo uso; falsos positivos de antivirus en Windows | Descartada |
| Reimplementar `init` y presets en Node | Copiaríamos el resolvedor de Spec Kit: deriva garantizada, justo lo que evita *componer, no bifurcar* | Descartada |
| **Instalación bajo demanda** | Necesita red la primera vez (ya la necesita para el modelo) | **Elegida** |

**Cómo funciona:** la primera vez que un proyecto activa SDD, la app busca en orden:

1. `specify` en la versión fijada → lo usa.
2. `uv` instalado → `uvx --from specify-cli==<versión>`.
3. Si no hay nada, baja **uv fijado y con SHA-256 verificado** a la carpeta de datos de la app; uv baja su propio Python administrado a su caché. Pasa una vez por máquina, no por proyecto.

Después corre `init` con el script del sistema (`ps` en Windows, `sh` en el resto) y la integración del runtime elegido, instala el preset y siembra la constitución en ese orden.

**Respaldo:** sin red, o con un proxy corporativo que bloquea PyPI o GitHub, la app lo explica y muestra los pasos manuales. Ahí el prerequisito vuelve como plan B.

**Seguridad:** versiones fijadas y checksums verificados. Es cadena de suministro, con el mismo criterio que las skills de terceros.

### Métricas

Salen todas del event store, así que medirlas no cuesta tokens. Cada una figura con la decisión que alimenta; las que no cambian una decisión (líneas de código, cantidad de agentes) quedan afuera.

| Métrica | Qué decisión alimenta |
| --- | --- |
| Costo y tokens por historia, por etapa (análisis, spec, plan, implementación, QA) y por rol | Dónde se va la plata; qué etapa recortar |
| Precisión de la estimación (estimado vs. real, en tokens y tiempo) | Calibrar la estimación (idea 2) |
| Escalados de nivel (rápido → estándar → máximo) por rol y tipo de tarea | Calibrar `model-routing` |
| Retrabajo: specs, planes y diffs rechazados en un gate; vueltas de feedback por tarea | Qué etapa produce mal; si el QA temprano paga |
| QA a la primera: AC verdes en la primera verificación | Calidad de spec e implementación |
| Defectos después del merge, vinculados a su historia | Si los gates dejan pasar cosas |
| Lead time por historia y **tiempo esperando al humano**, por gate | Si el nivel de autonomía es el cuello de botella |
| Hallazgos de seguridad por severidad y etapa (hook vs. revisión) | Dónde reforzar |
| Uso de skills y roles; skills instaladas y quitadas sin uso | Curar la biblioteca (notas 4 e idea 4) |
| Ratio de caché de prompts | La palanca de costo más grande y menos visible |
| Checkpoints disparados y cortes sin aviso | Si los umbrales del checkpoint están bien |

## Ideas tomadas de BMAD (19/10)

[BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD) va en el mismo sentido, pero es una metodología empaquetada en skills, no una plataforma: compite con Spec Kit y nuestro kit, no con la app. **No se adopta como base**, por tres motivos: corre Python en cada activación de skill, sus subagentes de revisión usan el mismo modelo que la sesión (lo opuesto a nuestra política de niveles) y la v7 está en alpha con cambios que rompen. Licencia MIT: se toman ideas.

| Idea | Dónde quedó en el kit |
| --- | --- |
| Tamaño objetivo del plan: 900 a 1.600 tokens (guía, no gate) | Envoltura de `speckit.plan` |
| Ruteo explícito por tamaño: ruta corta, normal o completa, anunciada con su motivo | `lead`, nueva sección *Ruteo por tamaño* |
| Revisión por lentes en paralelo: claims-check, borrados, AC sin cubrir, fuera de alcance | `qa` (modo verificación) y gate del `tasking` |
| Registro de errores de los agentes (pitfalls); al segundo, se propone regla en `AGENTS.md` | `close-story` §6.1, en Engram |
| Tickets como archivos en `tickets/` para proyectos sin tablero, y Linear como fuente | Envoltura de `speckit.specify`, `lead` y `.agents/mcp.json` |
| Discusión multi-perspectiva antes de una ADR cara (una ronda, 2 o 3 roles, niveles baratos) | Skill `adr`, §3.1 |

**Python en cada uso: no tiene ventaja que no podamos tener gratis.** `render_skill.py` arma cada skill en el momento de activarla: combina plantillas Jinja con la personalización del proyecto (TOML), evalúa condicionales, valida la configuración y deja el resultado cacheado por hash. Las ventajas son reales: personalizar sin bifurcar, cargar solo la rama de contenido que aplica y obligar a leer la skill entera (la imprime en vez de pedir que se lea un archivo). Pero se pagan en el lugar equivocado:

- **Una vuelta extra del modelo por activación:** el agente tiene que ejecutar un comando antes de saber qué hacer. Son tokens y latencia en cada uso.
- **Python y uv en cada máquina, en runtime.** Y con `uv run --no-cache`, que no reutiliza la caché de uv y puede volver a resolver `jinja2` en cada corrida: más lento y con dependencia de red.
- **El rol tiene que poder ejecutar comandos** para leer su propia skill.

Nuestra alternativa obtiene lo mismo sin pagar nada en runtime: el proyector (`tools/project.mjs`) y los presets de Spec Kit resuelven la composición al instalar o al proyectar, y el agente lee un archivo ya armado. Lo único que se pierde es la personalización por invocación (`--set clave=valor`), que no necesitamos.

**Idea 5 — Memoria por proyecto ("cerebro").** Meet, 16/10. A evaluar, con una propuesta inicial.

Hay dos memorias distintas, y una sola herramienta no cubre las dos:

| Memoria | Qué guarda | Opciones | Propuesta |
| --- | --- | --- | --- |
| **Del proyecto** | Decisiones, aprendizajes, preferencias, qué salió mal, resúmenes de fuentes | SQLite con FTS5 y [sqlite-vec](https://glama.ai/mcp/servers/Beledarian/mcp-local-memory), embeddings locales y un grafo de entidades y relaciones en tablas | **v1.** Va en el mismo SQLite por proyecto que ya tiene el event store. Embeddings locales: cero tokens para indexar. Se consulta por el MCP interno |
| **Del código** | Estructura: imports, llamadas, dependencias entre módulos | [Graphify](https://www.mindstudio.ai/blog/graphify-claude-code-knowledge-graph-large-codebase-70x), codebase-memory-mcp | **Opcional**, como conector. Según la fuente, no compensa por debajo de unos 500 archivos y la primera sesión no ahorra nada |

Reglas para que no envejezca mal:

- Los specs, las ADR y `AGENTS.md` siguen siendo la verdad. La memoria los indexa; no los reemplaza.
- **Se escribe al cerrar una historia**, desde `close-story`, no en cada turno. Escribir en cada turno es caro y mete ruido.
- **Todo recuerdo guarda su origen** (historia, archivo, fecha), para poder invalidarlo cuando ese origen cambia.
- **Se puede inspeccionar y borrar desde la UI.** Una memoria que no se ve no se puede corregir.

**Decisión (18/10): Engram de Gentleman Programming para la memoria del proyecto, detrás de un puerto `MemoryStore`, sujeto al spike.** Criterios: local, liviano, agnóstico al proveedor, aislado por proyecto, barato en tokens y con licencia compatible con un producto comercial.

| Opción | Pro | Contra | Veredicto |
| --- | --- | --- | --- |
| [Engram (Gentleman)](https://github.com/Gentleman-Programming/engram) | Binario Go sin runtime · SQLite + FTS5 · MIT · 16 herramientas MCP · resumen de sesión · sync por git en chunks (sirve para multiusuario) · soporta Claude Code, Codex, Gemini CLI y otros · 6,7k estrellas, versión 1.20 | Base única en `~/.engram/engram.db`: separa proyectos por campo, no físicamente · sin búsqueda semántica · 16 herramientas cuestan tokens de contexto en cada turno · otro almacén aparte del event store | **Elegida** |
| [engram.so](https://engram.so/) | MIT, MCP | Cloud-first; gratis solo 3 contextos; autoalojarlo suma un servicio | Descartada |
| [Basic Memory](https://docs.basicmemory.com/technical/technical-information) | Markdown como verdad + SQLite | **AGPL-3.0**: riesgo para un producto comercial | Descartada |
| [mcp-local-memory](https://glama.ai/mcp/servers/Beledarian/mcp-local-memory) | SQLite + sqlite-vec, embeddings locales, MIT | Proyecto chico, madurez sin verificar; descarga un modelo | Reserva si hace falta búsqueda semántica |
| Mem0, Graphiti, Zep | Grafo y semántica potentes | Docker, base vectorial o Neo4j, y llamadas a LLM en cada escritura | Descartadas por peso y costo |
| Propia | Aislamiento físico, un solo almacén, 2 o 3 herramientas | Construir y mantener lo que Engram ya resuelve | Plan B |

**Por qué Engram y no la propia:** resuelve el 80% del diseño (SQLite + FTS5 + MCP + resúmenes de sesión) con licencia MIT y sin runtime. La búsqueda solo por palabras es una ventaja de costo, no una carencia: no hay embeddings ni modelo que descargar.

**Condiciones, a validar en el spike** (si alguna falla, se va a la propia):

1. **Aislamiento por proyecto.** Para trabajo de consultoría, datos de dos clientes en el mismo archivo es un problema. Hay que verificar si se puede apuntar la base a `.workspace/` de cada proyecto; si no, la propia.
2. **Perfil mínimo de herramientas.** Exponer solo búsqueda, contexto y guardado, y medir cuántos tokens agregan sus definiciones por turno.
3. **Windows**, con el binario funcionando en una PC estándar.
4. **Borrado y exportación** desde la UI.

**Resultado de la verificación (18/10), sobre el código fuente.** No se pudo compilar en el entorno de análisis porque el proxy de módulos de Go está bloqueado; la prueba en una PC real queda para el spike.

| Condición | Resultado | Evidencia y cómo se usa |
| --- | --- | --- |
| Aislamiento por proyecto | ✅ | `ENGRAM_DATA_DIR` cambia la carpeta de datos por proceso. La app levanta un servidor por workspace apuntando a `<proyecto>/.workspace/engram/`: una base física por proyecto. Exige ruta absoluta y disco local (rechaza unidades de red) |
| Perfil mínimo y costo en tokens | ✅ con una trampa | `engram mcp --tools=mem_search,mem_context` expone solo esas dos: unos **420 tokens por turno**, contra unos **7.660 con las 23 por defecto** (estimado desde las descripciones del código). **Trampa:** si se registra `mem_save`, Engram inyecta la regla "guardá después de CADA decisión", que choca con el mandato de costos. Solución: los agentes solo leen y las escrituras las hace el lead por CLI (`engram save`) desde `close-story` |
| Windows | ✅ en papel | Builds oficiales para Windows amd64 y arm64; SQLite en Go puro (sin CGO), sin runtime; código y tests específicos de Windows. Falta probarlo en una PC estándar |
| Borrado y exportación | ✅ | `engram export` e `import`, exportación por proyecto y borrado por API local con token |

**A vigilar:** trae sincronización con Engram Cloud, que es opt-in y debe quedar apagada (sacaría datos de la máquina). El proyecto es muy activo, así que hay que fijar la versión.

**Veredicto: avanzamos con Engram.** Ya está en el kit (`.agents/mcp.json` y `close-story`). Si la prueba en Windows falla, el puerto `MemoryStore` permite pasar a la propia.

**División con lo que ya teníamos:** el checkpoint sigue siendo nuestro (necesita ramas y hashes para retomar). Engram guarda lo que se aprende, escrito al cerrar cada historia y al terminar la sesión, no en cada turno. El puerto `MemoryStore` hace que cambiar de motor cueste poco.
